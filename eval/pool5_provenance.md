# 질문 풀 5 (near-miss 답 없는 질문): 출처와 라벨링 기록

질문 풀 4(`eval/pool4_provenance.md`)의 답 없는 질문은 모두 '인접 주제'(다른 프레임워크, 클라우드 콘솔 절차 등)라 문서가 다루는 주제와 비교적 분명히 떨어져 있었고, 그 test(`qa_pool4_na_test_*`)는 v15 I4에서 이미 한 번 열었음. 운영에서 더 위험한 질문은 문서가 주제는 다루지만 묻는 핵심 하나가 없는 질문(검색은 관련 페이지를 찾고 모델은 빠진 세부를 지어낼 수 있음)이라, 그런 'near-miss' 질문을 새로 모은 풀. 질문 파일을 먼저 커밋하고 라벨은 그 커밋 뒤에 붙임(질문 풀 3·4와 같은 순서).

- `kind`는 라벨이 아님. 쓴 쪽의 의도일 뿐이고, 답이 있는지는 라벨을 붙이는 쪽이 문서를 찾아 정함(아래 '라벨'). near-miss로 쓴 질문이 실제로는 문서에 답이 있을 수 있어서(그래서 언어별 60개), 답 있음으로 밝혀진 near-miss는 따로 모아 거절 과잉을 보는 데 씀

## 누가 썼나 (질문)

- 2026-10-30, 별도의 LLM 에이전트 두 개(Claude Opus 5.5. 이 저장소 작업을 맡은 에이전트가 Claude Code를 비대화 모드(`claude -p`)로 따로 띄움)가 언어마다 하나씩 썼음. 한국어와 영어는 서로 다른 에이전트가 따로 썼으므로 한쪽이 다른 쪽의 번역이 아님
- 오염 통제 (질문 풀 4보다 엄격)
  - 도구를 하나도 주지 않음(`--tools ""`). 결과를 돌려주는 구조화 출력만 있었고, 실행 기록(stream-json)의 도구 호출은 두 에이전트 모두 그 한 번뿐이었음. 파일·웹·MCP 서버에 닿을 수단이 없었음
  - 기본 시스템 프롬프트 대신 짧은 고정 문장("평가 질문을 쓴다, 아무것도 찾아보지 말고 자기 지식만 쓴다")을 줌. 그래서 작업 폴더·환경 정보도 받지 않았음. 사용자 지침 파일·스킬·플러그인·MCP 설정은 끈 상태(`--safe-mode`, `--strict-mcp-config`)였고, 작업 폴더는 이 저장소 밖의 빈 폴더였음
  - 받은 맥락은 "FastAPI 공식 문서(영어와 한국어 번역)만 근거로 답하고, 문서에 답이 없으면 모른다고 해야 하는 RAG 도우미를 평가할 질문"이라는 설명과 아래 글쓰기 지시뿐임
- 그래도 그 모델은 학습으로 FastAPI 문서를 알고 있음. 질문 풀 3·4와 같은 한계임
- 글쓰기 지시: near-miss 정의(위 표, '검색하면 분명히 관련 페이지가 나오지만 그 페이지에 핵심이 없어서 답을 지어내고 싶어질 만한 질문'), FastAPI의 여러 영역에 고루 퍼지게 하고 목차를 따라가지 말 것, 개발자가 실제로 치는 말투(한국어는 번역투 없이, 식별자·오류 메시지는 원문대로), 짧은 사용법·증상·개념·비교·오류 메시지 인용을 섞을 것, 한두 문장 한 줄, 목록 안 중복 없이, 답할 수 없다는 티를 내지 말 것, 답은 쓰지 말 것

- **규칙** (질문 풀 4와 같고, 답 없음과 경계 사례를 더 자세히 정함)
  - `answerable: true`: 코퍼스 페이지 본문만으로 질문의 핵심(주로 묻는 것)에 답할 수 있음. 답하는 페이지를 모두 `expected_source_paths`에(지나가는 언급만 있는 페이지는 뺌), 답하는 절의 앵커를 `evidence`에 적음. 한국어 질문은 번역이 있으면 한국어 경로, 없으면 영어 경로(`english_only_page`). 핵심이 아니라 덜 중요한 곁가지만 빠지면 답 있음으로 두고 `notes`에 적음
  - `answerable: false`: 영어·한국어 트리에서 서로 다른 식별자·동의어·표현 세 가지 이상으로 찾아도 핵심에 답하는 페이지가 없음. 주제는 다루지만 묻는 세부(정확한 기본값·한도, 내부 동작, 버전 사이 차이, 경계 조건, 드문 조합)가 없으면 답 없음. `not_in_docs_evidence`에 `{"searched": [찾은 말], "finding": 어느 페이지가 주제를 다루고 무엇을 말하고 무엇을 말하지 않는지}`를 적음(문항마다 서로 다른 검색어 최소 3개, 중앙값 5개)
  - 불확실: 핵심의 일부만 답하거나, 간접 추론으로만 답이 나오거나, 질문을 얼마나 엄격히 읽느냐에 따라 갈리는 경계 사례는 기우는 쪽으로 채우고 불확실로 표시
  - 참고 답안은 문서 내용을 옮기지 않고 질문의 언어로 요약함. 답 없는 질문의 참고 답안은 '공식 문서가 다루지 않으며 그렇다고 밝히는 답이 맞다'이고, 바로 관련된 문서 내용이 있으면 한 구절 덧붙임
- **경계 사례 확인**: 라벨러가 불확실로 둔 20문항(한국어 14, 영어 6)을 세 번째 에이전트(언어마다 하나, 같은 조건·같은 지침, 첫 라벨은 보지 않고 질문만 받음)가 다시 붙였음. 세 번째 에이전트가 라벨러가 기운 쪽으로 **확정**한 3문항만 남기고(`boundary_check`에 두 판단을 적음), 반대로 확정한 2문항과 다시 불확실로 둔 15문항(그중 10문항은 라벨러와 같은 쪽으로 기욺)은 뺐음(`dropped`). 같은 쪽으로 기울어도 둘 다 확신하지 못한 문항은 라벨이 흔들리는 문항이라 셋에 넣지 않으려는 것

## 분할 (`eval/build_pool5_sets.py`, seed 20261030)

언어마다 답 없는 문항을 유형별로 따로 섞어 잘라(층화) dev와 test의 near-miss·인접 주제 비율을 맞춤. 거절률을 유형별로 보고하므로 dev에서 고른 설정을 test에서 같은 구성으로 재기 위함. dev의 인접 주제 몫은 round(10 × 인접 주제 수 / 답 없음 수)이고 나머지가 near-miss 몫. 답 있는 문항은 test 없이 모두 dev. `tests/test_pool5_sets.py`가 커밋된 셋이 이 결과와 같은지, 셋끼리 겹치지 않는지, 크기·유형 비율이 규칙대로인지 확인함.

| 셋 | 문항 (near-miss + 인접 주제) | 쓰임 |
|---|---|---|
| `qa_pool5_na_dev_ko`, `qa_pool5_na_dev_en` | 각 10 (8 + 2), 답 없음 | 튜닝용 |
| `qa_pool5_na_test_ko` | 42 (35 + 7), 답 없음 | 다음 거절 결정의 test. 한 번만 |
| `qa_pool5_na_test_en` | 52 (44 + 8), 답 없음 | 위와 같음 |
| `qa_pool5_ans_dev_ko`, `qa_pool5_ans_dev_en` | 6, 3 (모두 near-miss), 답 있음 | 거절 과잉(답할 수 있는데 모른다고 함) 확인용 dev. test 없음 |

- **답 없는 test의 사용 규칙**: 질문 풀 4의 '답 있는 test의 사용 규칙'과 같음. `qa_pool5_na_test_ko`·`qa_pool5_na_test_en`은 **한 결정에만** 씀. 어느 결정에 쓸지는 그 단계의 규칙에 측정 전에 적고, 그 결정에서 연 뒤에는 다른 결정의 조건에 넣지 않음(보고용으로만 다시 씀). test 크기가 30이 아니므로 '30문항 기준'으로 적은 문턱은 측정 전에 같은 비율로 다시 정함
- 거절률은 언어별 합계와 함께 유형별로도 봄: `python -m eval.refusal dev|test ... --by-kind`(문항 id의 `n`/`a`로 near-miss/인접 주제를 가름)
- 2026-10-30 기준 이 풀의 셋은 어떤 시스템으로도 열지 않았음

## 한계

- 질문을 LLM이 썼으므로 실제 사용자 질문의 분포·말투와 다를 수 있음(질문 풀 3·4와 같음). 쓴 모델은 학습으로 FastAPI 문서를 알고 있어서, 문서에 없을 것 같다고 고른 세부가 그 모델이 아는 범위로 치우쳤을 수 있음
- '없음'은 찾아본 말의 범위 안에서만 보인 것임. 라벨러가 떠올리지 못한 표현으로 문서 어딘가에 답이 있을 수 있어서 검색어와 찾은 내용을 남김. 세 번째 에이전트 확인은 라벨러가 불확실로 둔 문항에만 했고, 라벨러가 확정한 답 없음 113문항은 에이전트 하나의 판단임
- 경계 사례를 뺐으므로 남은 near-miss 답 없음은 문서가 '분명히' 답하지 않는 쪽으로 치우쳤음. 문서가 일부만 답하는 질문(판단이 가장 어려운 경우)의 거절은 이 풀로 잴 수 없음
- 답 있는 near-miss는 한국어 6, 영어 3문항뿐이라 거절 과잉은 거칠게만 볼 수 있음
- 유형은 쓴 쪽의 의도임. 인접 주제로 쓴 질문도 문서가 일부 다룰 수 있음(예: Nginx 뒤 SSE 버퍼링을 물은 `k5a05`는 문서에 `X-Accel-Buffering` 설명이 있어 경계 사례로 빠짐)
- 라벨은 모두 에이전트가 붙였고 사람 라벨은 없음. 정답 페이지 판단이 사람과 다를 수 있음
