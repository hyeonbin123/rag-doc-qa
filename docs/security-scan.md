# 보안 스캔 (DAST)

서비스 코드를 바꾼 뒤 실행 중인 API를 OWASP ZAP(무료, Apache-2.0)으로 스캔한다. 설정은 `zap/automation.yaml` 하나로, 베이스라인 부분(OpenAPI 설명 가져오기, 스파이더, 패시브 스캔)과 API 부분(기본 정책의 액티브 스캔)을 한 번에 돌린다. ZAP 2.17.0 공식 크로스플랫폼 패키지를 Java 17 이상으로 직접 실행한다 (Docker 없음).

## 대상

- `docker compose build`로 만든 API 이미지 그대로다. 다만 `zap/compose.scan.yml`로 두 가지를 바꿔 띄운다.
  - **DB 사본**: 스캔이 가입·질문 기록을 수백 건 쓰므로 `ragdb`를 복사한 `ragdb_scan`을 쓴다. 문서와 청크(벡터 포함)는 같다.
  - **생성기 대역**: 액티브 스캔은 `/query/ask`에 질문을 수백 번 보내는데, 실제 LLM이면 한 번에 몇 초씩 GPU를 쓴다. 그래서 Ollama의 `/api/chat`을 흉내 내는 표준 라이브러리 스크립트(`zap/ollama_stub.py`)가 정해진 답과 인용 JSON을 바로 돌려준다. 인증, 입력 검증, 언어 판별, 임베딩 모델, 벡터 검색, 질문 기록은 실제 코드가 돈다. 답변 문장은 정해진 문장이라 LLM 출력 자체는 스캔 대상이 아니다.
- 모든 요청에 스캔용 사용자(사본 DB에만 있음)의 `Authorization: Bearer` 토큰을 붙인다. ZAP이 대상 호스트로 가는 요청에 헤더를 붙이게 하는 환경 변수(`ZAP_AUTH_HEADER*`)로 넘기고, `zap/run_zap.sh`가 정한다. 토큰 하나로 스캔이 끝나도록 대상의 토큰 수명을 240분으로 늘린다.
- 관리자 적재 토큰은 ZAP에 주지 않는다. 적재는 GitHub에서 문서를 받아 DB를 바꾸는 작업이라 스캐너가 실행하지 않게 했다.
  - 1·2차: 대상에 관리자 토큰이 없고(관리자 적재 API 꺼짐) 계획도 `X-Admin-Token` 헤더를 보내지 않아, `POST /admin/documents/ingest`는 모두 헤더 필수 검사(422)에서 멈췄다. 그래서 토큰 비교 경로는 스캔되지 않았다.
  - 3차부터: 대상에 스캔마다 새로 만든 무작위 토큰(`SCAN_ADMIN_TOKEN`, 환경 변수로만 넘기고 저장하지 않음)을 설정해 관리자 적재 API를 켜 두고, 계획의 `requestor`가 틀린 값·빈 값·ASCII 밖 문자 값의 `X-Admin-Token`으로 관리자 요청 세 개를 보낸다. `activeScan-config` 작업으로 헤더도 공격 대상에 넣어(ZAP 기본은 쿼리·본문만), 스캐너가 이 헤더 값을 바꿔 가며 보낸다. 모두 '틀린 토큰(403)'이어야 하고 적재는 한 번도 돌지 않아야 한다.
- OpenAPI에서 만든 예시 질문에는 한글이 없어 영어 경로만 지난다. 그래서 한국어 질문 하나를 `requestor` 작업으로 보내 한국어 임베딩 경로도 액티브 스캔 대상에 넣는다.

## 실행

```bash
# DB만 띄운 상태에서 사본을 만들고 스캔 대상을 띄운다
docker compose up -d --wait db
docker compose exec -T db createdb -U raguser -T ragdb ragdb_scan
# 3차부터: 관리자 토큰을 스캔마다 새로 만들어 환경 변수로만 넘긴다(ZAP에는 주지 않음)
export SCAN_ADMIN_TOKEN=$(python -c "import secrets; print(secrets.token_urlsafe(32))")
docker compose -f docker-compose.yml -f zap/compose.scan.yml up -d --wait api
# 스캔용 사용자 (사본 DB에만 생김). 이메일과 비밀번호는 아무 값이나
curl -X POST localhost:8000/auth/register -H "Content-Type: application/json" \
  -d '{"email": "<이메일>", "password": "<8자 이상>"}'
TOKEN=$(curl -s -X POST localhost:8000/auth/login -d "username=<이메일>&password=<비밀번호>" \
  | python -c "import json, sys; print(json.load(sys.stdin)['access_token'])")
# ZAP_DIR은 zap-2.17.0.jar가 있는 폴더. 리포트(<이름>.json, <이름>.md)와 로그는 work/zap/<이름>/
# 6차부터: ZAP이 여는 메인 프록시(기본 127.0.0.1:8080, 스캔 계획은 쓰지 않음)가 같은 PC의 다른 서비스와 겹치지
# 않게 ZAP_PORT=<포트>로 옮길 수 있다(6차는 8095)
ZAP_DIR=<폴더> ACCESS_TOKEN=$TOKEN bash zap/run_zap.sh <이름>
```

## 3·4차 통과 기준 (2026-10-15, 3차 스캔 전에 적음)

3차 대상은 JWT 라이브러리 교체(python-jose → PyJWT, 같은 토큰 형식), 약한 JWT 비밀키 경고, compose 포트를 127.0.0.1로 묶기, `exec uvicorn`, 관리자 토큰 비교(`compare_digest`, 빈 값·공개 예시 값이면 꺼짐), 기본값이 꺼진 생성 설정 세 개를 넣은 커밋 뒤의 이미지다. 계획은 위 3차 변경(관리자 요청 세 개 + 헤더 공격)을 더했다.

- High 0, Medium 0, Low는 2차와 같은 40014 하나까지
- 500 응답 0, 앱 예외(api 컨테이너 로그의 Traceback) 0
- 관리자 적재 요청(`/admin/documents/ingest`)의 응답은 모두 307·403·405·422 중 하나이고, 403이 1건 이상(토큰 비교 경로를 실제로 지났다는 증거)
- 스캔 DB 사본 `ragdb_scan`의 documents·chunks 행 수와 `max(documents.fetched_at)`이 스캔 전과 같음(적재가 한 번도 돌지 않았다는 증거), 원래 DB `ragdb`의 행 수도 스캔 전과 같음
- 하나라도 어기면 원인을 고친 뒤 4차로 다시 돌린다. 이 기준은 결과를 보기 전에 정했다
- 4차(2026-10-15, 3차 결과 뒤): 같은 기준. 3차에서 기준을 어긴 High 1이 같은 사용자의 동시 쓰기 때문이었으므로(아래 표 3행), 액티브 스캔을 스레드 1개로 바꿔 '1'='1'·'1'='2' 요청 사이에 다른 요청이 끼지 않게 했다(`zap/automation.yaml`). 대상 이미지와 다른 계획은 3차와 같다
- 6차(2026-10-30, 스캔 전에 적음): 같은 기준, 5차와 같은 계획. 대상은 2026-10-24~30의 서비스 변경(생성기 장애 503과 422 본문의 제출값 제거, 청크의 제목 경로 바로잡기(청커 6판), 거절 분류기 좁히기, 적재 입력 검증과 동시 적재 409, 인증 오류 코드와 감사 로그, 시작 때 설정 범위 검사와 production의 문서 페이지 끄기, root가 아닌 사용자로 도는 이미지와 헬스체크, 질문 기록 한 번에 읽기와 인덱스, 기본값이 꺼진 고정 거절문 설정)을 모두 담아 새로 빌드한 이미지다. 다음 두 가지를 기준에 더한다
  - 스캔이 끝난 대상에 엔드포인트마다 검증에 걸리는 요청(필드 빠짐, 형식·범위 위반, 깨진 JSON, NUL 문자, 갱신 토큰 키 이름 틀림)을 보내면, 422 본문의 오류 항목에 `input`·`url`이 없고 보낸 값이 본문에 다시 나오지 않는다. 리포트에는 경보가 난 응답만 남아 스캔 요청 전체의 본문으로는 볼 수 없어서 따로 보낸다
  - `docker compose ... up -d --wait api`가 api 헬스체크가 healthy가 된 뒤에 돌아오고, 서버는 root가 아닌 사용자(uid 10001)로 돌며, 스캔 대상 환경의 `ANTHROPIC_API_KEY`는 비어 있다
- 6차에서 확인만 하는 것: 스캔 요청에 `GET /logs`의 새 `detail` 매개변수가 들어가는지(api 로그), 관리자 적재 요청의 403(틀린 토큰)마다 감사 로그 경고 줄이 하나씩 남는지. 생성기 대역은 늘 정상 답을 주므로 생성기 장애(503) 경로와 거절 답의 인용 비우기 경로는 스캔이 닿지 않는다(두 경로는 단위 테스트가 고정한다)
- 7차(2026-11-04, 스캔 전에 적음): 3·4차와 같은 기준, 6차와 같은 계획(액티브 스캔 스레드 1개, ZAP 메인 프록시는 `ZAP_PORT`로 8095). 대상은 이 줄을 더한 커밋에서 새로 빌드한 이미지다. 6차 대상(앱 파일이 `750aa76`과 같은 이미지) 뒤의 서비스 변경은 dense 검색의 정확 탐색 고정(`POST /query/ask`의 검색 트랜잭션에서 벡터 거리로 정렬하는 SQL 바로 앞에 `SET LOCAL enable_indexscan = off`를 보냄, `78bff12`, 그 주석만 고친 `a600e1c`), 시작할 때 `FASTAPI_DOCS_COMMIT_SHA`의 형식 검사(`445ce7b`), 의존성 잠금의 dnspython 2.9.1(`3a48282`), 설명 문자열만 한국어로 바꾼 `9cfa8da`다. 생성 쪽 거절 지시 실험(`docs/experiments.md`의 v16-B)은 채택되지 않아 서비스 기본값은 바뀌지 않았다. 6차에 더한 두 기준(422 본문, 이미지·헬스체크)은 이번 변경이 그 코드(`app/main.py`의 검증 오류 처리, Dockerfile, compose 설정)를 바꾸지 않아 아래 '확인만 하는 것'에 둔다. 이 기준은 결과를 보기 전에 정했다
- 7차에서 확인만 하는 것: (가) 스캔 동안 `POST /query/ask`가 질문 기록을 남겼는지. `ragdb_scan`의 `query_logs` 행 수가 ZAP 시작 직전보다 늘었으면 고정이 든 검색 경로를 실제로 지난 것이다(늘어난 수가 api 로그의 `POST /query/ask` 200 수와 같은지도 본다) (나) ZAP을 돌린 시간 범위의 db 컨테이너 로그에 PostgreSQL 경고 `SET LOCAL can only be used in transaction blocks`가 0줄인지. 고정 문장이 트랜잭션 밖에서 실행되면 아무 효과 없이 이 경고만 남는다. 이 경고가 db 로그에 남는다는 것은 스캔 전에 같은 문장을 트랜잭션 밖에서 한 번 보내 먼저 확인한다 (다) 6차에 더한 두 기준의 항목을 6차와 같은 방법으로: 스캔이 끝난 대상에 보내는 422 확인 요청(오류 항목에 `input`·`url`이 없고 보낸 값이 본문에 다시 나오지 않음), `up -d --wait api`가 api 헬스체크가 healthy가 된 뒤에 돌아옴, 서버가 uid 10001로 돎, 스캔 대상 환경의 `ANTHROPIC_API_KEY`가 빈 값. 6차에서 확인만 한 두 가지(`GET /logs`의 `detail` 매개변수, 틀린 관리자 토큰 403마다 감사 로그 경고 한 줄)도 같은 방법으로 센다
- 8차(2026-11-07, 스캔 전에 적음): 3·4차와 같은 기준, 7차와 같은 계획(액티브 스캔 스레드 1개, ZAP 메인 프록시는 `ZAP_PORT`로 8095). 대상은 이 줄을 더한 커밋에서 새로 빌드한 이미지다. 7차 대상(앱 파일이 `f501135`·`26a8d70`과 같은 이미지) 뒤의 서비스 변경은 관리자 적재의 오류 응답(GitHub가 모르는 `commit_sha`는 422, GitHub에 닿지 못했거나 GitHub가 오류 상태로 답하면 502, OpenAPI에 두 응답을 적음 — `375855f`, 그리고 commits 조회의 404를 모르는 ref가 아니라 502로 가른 `b49145f`), 이미지에 tiktoken 인코딩을 미리 넣어 서버가 인터넷 없이 시작하게 한 Dockerfile(`1381000`), compose db 헬스체크의 `pg_isready`에 `-d`를 준 것(`fa23dc1`), 설정 파일 주석만 바꾼 `3016255`, 검색 주석만 바꾼 `9c5c0b3`·`55e124e`다. 생성 쪽 거절 지시 실험은 7차 때처럼 채택되지 않은 채라 서비스 기본값은 그대로다. 이번에는 Dockerfile과 compose가 바뀌었으므로 6차에 더한 두 기준 가운데 이미지·헬스체크 기준(`up -d --wait api`가 api 헬스체크가 healthy가 된 뒤에 돌아옴, 서버가 uid 10001로 돎, 스캔 대상 환경의 `ANTHROPIC_API_KEY`가 빈 값)은 다시 통과 기준에 넣고, 422 본문 기준은 그 코드(`app/main.py`의 검증 오류 처리)가 바뀌지 않아 7차처럼 확인만 하는 것에 둔다. 기준에 더하는 것: ZAP을 돌린 시간 범위와 db를 띄운 뒤 전체의 db 컨테이너 로그에 FATAL 줄이 0줄(7차에는 헬스체크가 5초마다 남긴 `database "raguser" does not exist` 73줄이 있었고, 이 줄을 없애는 것이 compose 변경의 목적이다). 관리자 적재 요청은 ZAP이 관리자 토큰을 모르므로 7차처럼 모두 307·403·405·422로 끝나야 하고, 새 422(모르는 ref)·502 경로에는 닿지 않는다(그 두 경로와 404의 분류는 단위 테스트 `tests/test_documents.py`·`tests/test_ingestion.py`가 고정한다. 실제 GitHub에 붙는 확인 요청은 네트워크와 GitHub의 상태에 기대므로 넣지 않는다). 이 기준은 결과를 보기 전에 정했다
- 8차에서 확인만 하는 것: (가) 대상의 `/openapi.json`에서 `POST /admin/documents/ingest`의 응답 목록에 422(`HTTPValidationError` 참조)와 502가 있는지. ZAP은 이 문서로 요청을 만들므로 스캔 계획에도 그대로 들어간다 (나) 이미지와 서버 프로세스의 `TIKTOKEN_CACHE_DIR`이 `/opt/tiktoken`이고, 그 폴더에 인코딩 파일 하나가 있으며 그 sha256이 tiktoken이 기대하는 값과 같고, 실행 사용자(app)가 그 폴더에 쓸 수 없는지(인터넷 없이 시작하는 것 자체는 `1381000` 때 `--network none`으로 확인했고, 스캔 대상은 인터넷이 있는 네트워크에서 띄운다) (다) 7차에서 확인만 한 세 가지를 같은 방법으로: 스캔 동안 늘어난 `ragdb_scan`의 `query_logs` 수 = api 로그의 `POST /query/ask` 200 수, ZAP 시간 범위의 db 로그에 `SET LOCAL can only be used in transaction blocks` 0줄(스캔 전 대조 실험 1줄), 스캔이 끝난 대상에 보내는 422 확인 요청 27개(오류 항목에 `input`·`url`이 없고 보낸 값이 본문에 다시 나오지 않음). 6차에서 확인만 한 두 가지(`GET /logs`의 `detail` 매개변수, 틀린 관리자 토큰 403마다 감사 로그 경고 한 줄)도 같은 방법으로 센다
