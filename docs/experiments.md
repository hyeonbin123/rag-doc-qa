# 검색 품질 실험 기록 (v1 ~ v9)

README의 측정 결과 요약에 대한 자세한 기록. 각 리포트 원본은 `eval/reports/`에 있음.

## 평가 방식

- **질문셋**
  - `eval/qa_dataset.jsonl`: 30문항. v1~v6의 테스트셋
  - `eval/qa_dev.jsonl`: 32문항, v5부터 쓴 튜닝 전용 검증셋
  - `eval/qa_test2.jsonl`: 43문항, v7에서 쓴 새 테스트셋
  - `eval/qa_test2_ko.jsonl`: 43문항, v8에서 쓴 한국어 테스트셋. qa_test2의 질문을 자연스러운 한국어로 바꾸고 정답을 한국어 번역 문서로 연결함
  - `eval/qa_dev_ko.jsonl`: 32문항, v9부터 쓴 한국어 튜닝용 셋. qa_dev의 질문을 한국어로 옮기고 정답을 한국어 번역 문서로 연결함
- **검색 지표**: Hit@k(정답 문서가 상위 k개 안에 있는 비율), MRR(정답 문서 순위의 역수 평균), 검색 단계 지연(p50/p95)
- **답변 지표**: 키워드 커버리지, LLM 판정 충실도·정확도(1~5점, JSON 스키마로 범위 강제), 환각 판정 수
- **원칙**: 파라미터는 검증셋에서만 고르고, 테스트셋에는 고른 설정 하나만 돌림. 기본값을 바꾸는 조건은 측정 전에 정함.

## v1 → v3: 청킹 개선

| 버전 | 변경 | Hit@3 | Hit@10 | MRR |
|---|---|---|---|---|
| v1 | 기본 청커 | 0.93 | 0.97 | 0.828 |
| v2 | MkDocs 마크업 정제 (헤딩 앵커 ID, 코드 include 지시문, admonition, HTML 태그) | 0.97 | 0.97 | 0.911 |
| v3 | v2 + `<dfn>`/`<abbr>` 정의 텍스트 보존 | 0.97 | 0.97 | **0.933** |

- **진단**: 실패한 문항의 상위 10개 유사도가 0.72~0.76의 좁은 구간에 몰려 있었음. 이 구간에서는 모든 헤딩에 붙은 `{ #anchor-id }`(제목이 임베딩에 두 번 들어감)나 실제 코드 없이 경로만 있는 include 지시문 같은 마크업 노이즈가 순위를 좌우함.
- **v2**: 마크업 정제로 MRR 0.828 → 0.911. 백그라운드 작업 질문(q006)이 6위에서 1위로 올라감. 대신 q011은 1위에서 3위로 **회귀**.
- **v3**: 회귀 원인은 정제 로직이 `<dfn title='..."cleanup code"...'>`의 title 속성까지 지운 것이었음. 질문에 나온 "cleanup code"가 바로 그 안에 있었음. 정의 텍스트를 "용어 (정의)" 형태로 보존해 q011을 복구했고 MRR은 0.933.
- 청커를 바꾸면 수집 해시가 달라지도록 `CHUNKER_VERSION`을 해시에 포함함. 원문 해시만 쓰면 청커를 바꿔도 재수집 때 모든 문서가 "변경 없음"으로 스킵되어, 예전 청크로 측정하게 되기 때문.

## v4: 하이브리드 검색 (ts_rank + RRF, 기본값으로 채택하지 않음)

q017처럼 dense 임베딩이 의미를 혼동하는 경우를 보완하려고, Postgres 전문 검색(생성 컬럼 `tsvector` + GIN 인덱스) 순위와 dense 순위를 RRF(Reciprocal Rank Fusion, k=60)로 합치는 모드를 추가하고 같은 30문항으로 비교함.

| 모드 | Hit@3 | Hit@10 | MRR |
|---|---|---|---|
| dense (v3와 문항 단위까지 동일) | 0.97 | 0.97 | **0.933** |
| hybrid | 0.97 | **1.00** | 0.898 |

- **얻은 것**: q017이 top-10 밖에서 9위로 들어옴. 어휘 검색만 놓고 보면 settings.md가 **1위**였음.
- **잃은 것**: q001(1위→2위), q009(1위→2위), q003(2위→3위). 두 문항 모두 어휘 검색 상위 5개에 정답 문서가 없었고, q009는 모든 기능을 언급하는 `release-notes.md`가 어휘 검색 1위였음.
- **원인**: Postgres `ts_rank`에는 BM25의 IDF(역문서빈도)가 없어서 흔한 단어와 드문 단어를 같은 무게로 셈. "fastapi"는 청크 915개 중 524개(57%)에, "parameter"는 258개(28%)에 나오기 때문에, 질문 단어를 OR로 묶은 어휘 순위가 잡음이 되고, 가중치가 같은 RRF가 그 잡음 때문에 dense의 1위를 밀어냄.
- **결정**: 처음 정한 기준(평균이 나아질 때만 기본값 변경)에 따라 dense를 유지하고, hybrid는 `RETRIEVAL_MODE=hybrid`로 켤 수 있게 남김. 이 30문항에 맞춰 가중치를 고르면 평가셋에 과적합되므로 튜닝하지 않음.
- **구현 메모**: 질문 단어는 OR로 묶음. `plainto_tsquery`는 모든 단어를 AND로 묶어서 문장형 질문으로는 거의 아무것도 걸리지 않음. dense 후보는 40개로 제한함. pgvector HNSW 스캔은 한 번에 `hnsw.ef_search`(기본 40)개까지만 돌려주기 때문.

## v5: BM25 + 검증셋 분리 (기본값으로 채택하지 않음)

v4에서 hybrid가 진 원인으로 `ts_rank`에 IDF가 없다는 점을 지목했으므로, 어휘 순위를 BM25로 바꾸고, 튜닝에 쓰는 질문과 평가에 쓰는 질문을 나눠 다시 측정함.

- **검증셋 분리**: 튜닝 전용 `eval/qa_dev.jsonl` 32문항을 새로 작성하고, 기존 30문항(`qa_dataset.jsonl`)은 테스트셋으로만 씀. 검증셋은 테스트셋이 정답으로 쓰는 문서를 주 정답으로 삼지 않음(보조 정답으로 settings.md, metadata.md 두 개만 겹침). 정답 경로가 DB에 있는지, 기대 키워드가 정답 문서에 실제로 있는지는 스크립트로 확인함.
- **BM25를 SQL로 구현** (`app/services/retrieval.py`): 확장이나 통계 테이블을 추가하지 않음. 질문 어휘소별 문서 빈도(df)는 GIN 인덱스로 세고, 청크 안 빈도(tf)는 `tsvector`의 위치 개수에서, 길이는 `token_count`에서 가져옴 (k1=1.2, b=0.75 기본값, 튜닝하지 않음). ParadeDB `pg_search`는 DB 이미지를 바꿔야 하는데, 이 규모(청크 915개, 어휘 검색 1회 약 40~50ms)에서는 SQL로 충분하다고 판단함. 드문 단어가 반복된 흔한 단어보다 높게 평가되는지는 단위 테스트로 고정함.
- **절차 (측정 전에 정함)**: RRF에서 BM25 목록의 가중치(dense 목록은 1)만 {0.25, 0.5, 0.75, 1.0} 중 검증셋 MRR로 고르고, 고른 설정 하나만 테스트셋에 한 번 돌림. 기본값은 검증셋과 테스트셋 **모두**에서 dense보다 나을 때만 바꿈.

| 설정 | 검증셋 MRR (32문항) | 테스트셋 MRR (30문항) |
|---|---|---|
| dense | 0.858 | **0.933** |
| hybrid, ts_rank (v4) | **0.953** | 0.898 |
| hybrid, BM25 가중치 0.25 / 0.5 / 1.0 | 0.884 / 0.906 / 0.922 | 돌리지 않음 |
| hybrid, BM25 가중치 0.75 (검증셋에서 선택) | **0.953** | 0.894 |

- **결과**: hybrid는 검증셋에서 dense보다 0.095 높았지만 테스트셋에서는 0.039 낮음. 규칙대로 기본값은 dense를 유지하고, hybrid 모드의 어휘 순위를 BM25(가중치 0.75)로 바꿔 opt-in으로 남김.
- **BM25 자체는 의도대로 동작함**: q017의 BM25 순위에서 settings.md가 1위, environment-variables.md가 2위임 (IDF: secret·credential 3.90, fastapi 0.56). q009는 v4에서 2위였던 header-params.md가 1위로 돌아옴.
- **그런데 q017은 최종 결과에서 top-10 밖으로 밀림**: settings.md는 dense 상위 40개에 한 번도 들지 않아서 RRF 점수가 0.75/61 ≈ 0.012에 그침. 반면 두 목록 모두에 걸린 인증 문서 청크는 1/(60+순위)를 두 번 받음(예: 1/65 + 0.75/70 ≈ 0.026). RRF는 두 목록이 모두 적당히 올린 결과를 한 목록만 1위로 올린 결과보다 높게 치는 구조임. q001은 BM25에서 "hint"(IDF 3.66)가 드문 단어라 python-types.md가 1~3위를 차지했고, 최종 순위는 1위에서 3위로 내려감.
- **해석**: 문항 하나가 1위에서 2위로 내려가면 MRR이 약 0.016 바뀜. 가중치별 곡선이 단조롭지 않고(0.884 → 0.906 → 0.953 → 0.922) 두 셋이 반대 방향을 가리키는 것으로 보아, 30문항 규모로는 dense와 hybrid의 차이를 가려내기 어려움. 두 셋을 합친 62문항 평균은 hybrid(약 0.92)가 dense(약 0.89)보다 높지만, 결과를 본 뒤 규칙을 바꾸면 검증셋을 따로 만든 의미가 없어지므로 기본값은 그대로 둠. 두 셋 모두 문서를 읽으면서 작성해서 질문과 본문의 단어가 겹치기 쉽고, 이 편향은 어휘 검색 쪽에 유리하게 작용할 수 있음.

## v6: Cross-encoder 재정렬 (기본값으로 채택하지 않음, 답변 품질은 개선)

v5에서 q017의 정답이 BM25 순위로는 1위인데 RRF 구조 때문에 밀리는 것을 확인했음. 그래서 `RETRIEVAL_MODE=rerank`를 추가함. 두 목록의 후보를 합친 뒤, cross-encoder(`cross-encoder/ms-marco-MiniLM-L-6-v2`)가 질문과 후보 본문을 함께 읽고 다시 채점함 (`app/services/reranking.py`, `rerank_search`). 모델 호출은 CPU를 오래 쓰므로 스레드에서 실행해 이벤트 루프를 막지 않음.

**측정 전에 정한 절차**
- **지연 예산**: 검색 단계 지연 중앙값 1초 이하 (전체 응답 약 4.6초의 약 20%). 후보 40개 기준 CPU 측정값은 MiniLM-L6 약 3.3초, MiniLM-L12 약 6.5초, bge-reranker-base 약 20초였음. 그래서 모델은 MiniLM-L6으로 고정함
- **튜닝**: 각 목록에서 가져올 후보 수만 {5, 10, 20} 중에서, 예산 안에 드는 설정끼리 검증셋 MRR로 고름. 테스트셋에는 고른 설정 하나만 돌림
- **기본값 변경 조건**: 검증셋과 테스트셋 모두에서 MRR이 dense보다 높고, 지연이 예산 안일 것

검증셋 (32문항):

| 설정 | MRR | 지연 p50 | 지연 p95 |
|---|---|---|---|
| dense | 0.858 | 10ms | 52ms |
| rerank, 목록당 5개 | **0.969** | 627ms | 911ms |
| rerank, 목록당 10개 | 0.953 | 1383ms (예산 초과) | 1786ms |
| rerank, 목록당 20개 | 0.945 | 2700ms (예산 초과) | 3480ms |

테스트셋 (30문항, 목록당 5개로 1회만 실행):

| 설정 | Hit@3 | Hit@10 | MRR | 지연 p50 |
|---|---|---|---|---|
| dense | 0.97 | 0.97 | **0.933** | 9ms |
| rerank | **1.00** | **1.00** | 0.889 | 620ms |

- **결과**: 테스트셋 MRR이 dense보다 낮으므로(0.889 < 0.933) 규칙대로 기본값은 dense를 유지함. rerank는 설정으로 켤 수 있게 남김.
- **얻은 것**: q017이 top-10 밖에서 1위로 올라옴. 테스트셋 30문항 모두 정답 문서가 3위 안에 들어옴(Hit@3 0.97 → 1.00).
- **잃은 것**: dense에서 1위였던 q001·q013은 3위로, q009는 2위로 내려감. 정답 문서는 여전히 3위 안에 있지만 1위가 아니게 되어 MRR이 떨어짐.

**답변 품질 (참고용, 결정에는 쓰지 않음)**

LLM은 top-5를 모두 읽으므로, 정답이 몇 위인지보다 top-5 안에 들었는지가 더 중요할 수 있음. 그래서 같은 날 같은 모델로 두 모드 모두 답변 평가를 돌림. dense 결과는 집계가 v3 리포트와 소수점까지 같아서, 아래 차이를 실행할 때마다 생기는 편차로 보기는 어려움.

| 지표 | dense | rerank |
|---|---|---|
| 키워드 커버리지 | 0.93 | **1.00** |
| 충실도 (1-5) | 4.17 | **4.27** |
| 정확도 (1-5) | 4.73 | **4.87** |
| 판정 모델이 환각으로 표시 | 1/30 | **0/30** |

- 충실도·정확도의 합계 차이는 q017 한 문항의 변화와 크기가 같음 (충실도 1 → 4, 정확도 1 → 5). 순위가 내려간 q001·q009·q013은 두 모드의 점수가 같음 (커버리지 1.00, 충실도 4, 정확도 5).
- **해석**: 검색 순위(MRR)로 보면 dense가, RAG 전체 결과(정답 문서가 top-5에 드는지, 답변 품질)로 보면 rerank가 나음. 차이는 사실상 q017 한 문항에서 나오고, 비용은 검색 지연 약 +0.6초임. 기준을 답변 품질로 바꾸려면 이 결과를 보고 바꿀 게 아니라, 새로 만든 테스트셋에서 미리 정한 기준으로 다시 확인해야 함 (v7).

## v7: 새 테스트셋에서 답변 정확도로 재판정 (동점, 기본값 dense 유지)

v6에서는 검색 순위(MRR)로 보면 dense가, 답변 품질로 보면 rerank가 나았음. 기준을 바꾸려면 새 질문으로 다시 확인해야 하므로, 새 테스트셋을 만들고 판단 기준부터 정함.

**측정 전에 정한 절차**
- **새 테스트셋** `eval/qa_test2.jsonl` (43문항)
  - 사용자 입장에서 질문 44개를 먼저 썼음 (`eval/qa_test2_draft.md`). 정답 문서는 그다음에 DB를 검색해서 찾음
  - 기존 두 셋은 문서를 읽으면서 작성해서 질문과 본문의 단어가 겹치기 쉬웠는데, 이 방식은 그 편향을 줄임
  - 코퍼스에 설명이 없는 1문항(API 키 헤더)만 빼고, 나머지 질문 문구는 바꾸지 않음
- **주 지표**: 답변 정확도 평균 (LLM 판정 1~5점). 모델은 상위 5개를 모두 읽으므로 순위보다 최종 답변을 봄
- **보조 조건**: Hit@5가 dense보다 낮지 않을 것
- **동점이면 dense**: 검색 지연이 약 0.55초 적기 때문

검색 (43문항):

| 설정 | Hit@3 | Hit@5 | Hit@10 | MRR | 지연 p50 |
|---|---|---|---|---|---|
| dense | 0.86 | 0.88 | 0.95 | 0.786 | 9ms |
| rerank | **0.91** | **0.93** | 0.95 | **0.811** | 562ms |

답변 (43문항, 같은 날 같은 모델):

| 지표 | dense | rerank |
|---|---|---|
| 정확도 (1-5, 주 지표) | 4.60 | 4.60 |
| 충실도 (1-5) | 4.12 | **4.23** |
| 키워드 커버리지 | 0.79 | **0.88** |
| 판정 모델이 환각으로 표시 | 0/43 | 0/43 |

- **결과**: 보조 조건은 통과했지만(Hit@5 0.88 → 0.93) 주 지표가 동점임. 43문항 합계가 두 모드 모두 198점이라, 규칙대로 기본값은 dense를 유지함.
- **문항별 변화는 크지만 서로 상쇄됨**: rerank에서 정확도가 오른 문항이 8개(합계 +10점), 내린 문항이 7개(합계 −10점)임.
  - **t001 (CORS)**: dense에서는 정답 문서가 9위라 LLM에 전달되지 않았고 2점을 받음. rerank에서는 5위 안에 들어와 5점이 됨.
  - **t036 (X-Token 헤더)**: 두 모드 모두 정답 문서가 1위였는데 점수는 5 → 2로 떨어짐. 정답 문서의 순위가 같아도, 함께 전달되는 나머지 청크가 바뀌면 7B 모델의 답이 달라짐.
  - **t030**: rerank가 정답 문서를 1위로 올렸지만, 답변이 WebSockets를 설명해 2점을 받음. WebSockets 문서도 정답으로 인정해 놓고 참고 답안은 SSE 중심으로 쓴 탓으로, 질문셋 설계의 약점임.
- **해석**: 이 규모에서 재정렬은 정답 문서가 상위 5개에 드는 비율은 올리지만, 답변 정확도의 평균은 바꾸지 못함. 컨텍스트 구성이 바뀔 때 7B 생성 모델과 판정 모델이 문항마다 다르게 반응하고, 그 흔들림이 개선분을 덮음. 그래서 기본값은 dense로 확정하고 rerank는 설정으로 남김. 효과를 더 끌어내려면 검색보다 생성 모델을 바꾸거나 판정을 여러 번 해서 평균을 내는 쪽이 먼저임.
- **두 모드 모두 못 찾는 문항**
  - **t010 (파일 다운로드)**: dense는 업로드 문서를, BM25는 "download"가 들어간 다른 문서를 가져옴.
  - **t043**: 질문은 "필드"를 말하지만, 코퍼스는 이 기능을 "쿼리 파라미터" 기준으로 설명함.

## v8: 한국어 문서·질문 지원 (언어별 임베딩 모델, 규칙과 다른 결정)

FastAPI 공식 문서에는 한국어 번역(`docs/ko/docs/`)이 있음. 영어 문서 155개 중 124개가 번역돼 있고, 번역이 없는 것은 API 레퍼런스, 릴리스 노트, 커뮤니티 페이지뿐임. 이를 함께 적재하고, 한국어 질문은 한국어 문서에서 찾도록 함.

**구현**
- 청크마다 언어(`en`, `ko`)를 저장함 (마이그레이션 0003). 질문에 한글이 있으면 한국어로 판별하고, 그 언어의 청크만 검색함
- 임베딩 모델은 쿼리·패시지 접두사를 모델별로 둠: BGE는 지시문, E5는 `query:` / `passage:`
- 수집 해시에 임베딩 모델 이름을 넣음. 청커 버전과 같은 이유로, 모델을 바꾸면 해당 문서가 자동으로 다시 임베딩됨
- 답변 프롬프트는 한국어 질문일 때만 "한국어로 답하고, 코드와 API 이름은 그대로 둔다" 규칙을 덧붙임
  - 처음에는 모든 질문에 "질문과 같은 언어로 답하라(예: 한국어 질문에는 한국어로)" 규칙을 넣었음
  - 그랬더니 로컬 7B 모델이 영어 질문에도 한국어로 답했고, 영어 테스트셋 2의 답변 정확도가 4.60에서 4.19로 떨어짐 (16문항 하락, 합계 198 → 180)
  - 검색 결과는 이전과 같았으므로 원인은 프롬프트였음
  - 그래서 영어 프롬프트는 원래 문장 그대로 두고(테스트로 고정), 한국어 규칙은 한국어 질문에만 붙이도록 바꿈

**측정 전에 정한 규칙**
- 후보: 기존 `bge-small-en`과 다국어 `multilingual-e5-small`. 벡터 크기가 384로 같고 CPU 속도도 비슷함. `bge-m3`는 CPU에서 전체 적재에 1시간이 넘게 걸려 제외했고, `multilingual-e5-base`는 3.4배 느린데 간단한 비교에서 품질 차이가 작아 제외함
- 판단: 영어 튜닝용 셋에서 다국어 모델의 MRR 하락이 0.03 이하면 모델 하나로 통일함. 더 떨어지면 영어는 기존 모델을 유지하고 한국어만 다국어 모델을 씀
- 한국어 테스트셋 `qa_test2_ko.jsonl`은 새로 만들었음. v7의 테스트셋(질문을 먼저 쓰고 정답을 나중에 찾은 셋)을 한국어로 옮김

**결과 (dense, 공정한 비교를 위해 같은 문서 스냅숏을 두 DB에 각각 적재)**

| 질문셋 | bge-small-en | multilingual-e5-small |
|---|---|---|
| 영어 튜닝용 (판단 기준) | 0.858 (정확 탐색 기준) | **0.870** |
| 영어 테스트셋 1 (30문항) | **0.933** | 0.638 |
| 영어 테스트셋 2 (43문항) | **0.786** | 0.705 |
| 한국어 테스트셋 (43문항) | 0.250 | **0.609** |

- **규칙대로라면 모델 하나로 통일해야 했음**: 튜닝용 셋에서는 다국어 모델이 오히려 높았기 때문
- **그러나 두 영어 테스트셋에서 크고 일관된 하락이 나옴**
  - 테스트셋 1: 14문항이 떨어지고 오른 문항은 없음
  - 테스트셋 2: 10문항이 떨어지고 4문항이 오름
  - 문항 하나 차이로 흔들리는 수준이 아님. 튜닝용 셋은 문서를 보며 쓴 셋이라 API 이름이 들어간 질문이 많았고, 이 차이를 잡아내지 못함
- **결정**: 규칙을 따르면 영어 품질이 크게 떨어진다는 것을 이미 알고 배포하게 됨. 규칙의 목적은 영어 품질을 지키는 것이었으므로, 규칙과 다르게 영어는 기존 모델을 유지하고 한국어에만 다국어 모델을 씀
  - 이 결정은 영어 결과를 전혀 바꾸지 않으므로, 결과를 부풀릴 여지가 없음
  - 교훈: 튜닝용 셋 하나에만 안전장치를 걸면, 그 셋의 편향이 그대로 판단을 흔듦
- **언어별 벡터 인덱스** (마이그레이션 0004)
  - 두 모델의 벡터는 서로 다른 공간이라 하나의 HNSW 그래프로 탐색하면 안 됨
  - 그래서 언어별 부분 인덱스를 두고, 검색 SQL에는 언어를 리터럴로 넣어 플래너가 해당 인덱스를 쓰게 함. 값은 지원 언어 목록으로 검사한 뒤에 넣음
  - 실행 계획으로 영어 질문은 `chunks_embedding_en_hnsw_idx`, 한국어 질문은 `chunks_embedding_ko_hnsw_idx`를 쓰는 것을 확인함
- **측정 중 겪은 문제 (d024)**
  - 전체 재적재 직후, 영어 튜닝용 셋에서 한 문항(d024)이 빠져 MRR이 0.858에서 0.827이 됨. 정확 탐색에서는 그대로 찾았음
  - 처음에는 한국어 벡터가 섞인 인덱스나 인덱스 재생성 탓으로 봤지만, 언어별 인덱스로 바꾼 뒤에도 같은 현상이 나와서 틀린 추정이었음
  - 시간을 대조해 보니, 0.827이 나온 평가는 자동 VACUUM이 끝나기 8초 전에 끝났고, VACUUM 이후 다시 돌리니 0.858로 돌아옴
  - 재적재로 지워진 이전 청크(dead tuple)가 인덱스에 남아 탐색 후보 자리를 차지한 것으로 봄. 그래서 적재가 문서를 바꾸면 곧바로 `VACUUM (ANALYZE) chunks`를 실행하게 함

## v9: 한국어 질문에 다국어 재정렬 모델 적용

v8에서 한국어는 dense만 측정했음. 한국어 테스트셋 MRR(0.609)이 같은 질문의 영어판(0.786)보다 낮아서, 다국어 재정렬 모델을 붙여 봄. 기존 재정렬 모델(MS MARCO MiniLM-L6)은 영어로만 학습돼 한국어에는 맞지 않음.

**측정 전에 정한 절차**
- **한국어 튜닝용 셋** `eval/qa_dev_ko.jsonl` (32문항)
  - 영어 튜닝용 셋의 질문을 한국어로 옮기고, 정답을 한국어 번역 문서로 연결함. 32문항 모두 정답 문서의 번역이 있음
  - 5문항(kd004, kd007, kd009, kd012, kd013)은 정답 문서가 한국어 테스트셋과 겹침. 질문은 서로 다르고 고르는 설정이 몇 개뿐이라 그대로 둠
  - 한국어 dense 기준값: MRR 0.766
- **후보 모델**: `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`. MS MARCO를 여러 언어로 옮긴 데이터(mMARCO)로 학습한 다국어 모델로, 기존 모델과 같은 계열임
  - 품질은 보지 않고 지연만 먼저 잼 (한국어 청크 80쌍): 쌍당 약 100ms. 기존 영어 모델은 약 60ms, `bge-reranker-base`는 약 320ms
  - `bge-reranker-base`는 예산 안에서 후보를 3개 정도밖에 볼 수 없어서 제외함
- **지연 예산**: v6과 같이 검색 단계 지연 중앙값 1초 이하
- **튜닝**: 목록당 후보 수를 {3, 5, 8} 중에서, 예산 안에 드는 설정끼리 한국어 튜닝용 셋 MRR로 고름. 튜닝용 셋에서도 dense보다 낮으면 테스트셋은 돌리지 않음
- **한국어 기본값 변경 조건** (v7과 같은 규칙, 한국어 테스트셋 43문항)
  - 주 지표: 답변 정확도 평균이 dense(4.07)보다 높을 것
  - 보조 조건: Hit@5가 dense(0.77)보다 낮지 않을 것
    - 처음에는 기준값을 0.72로 잘못 적었음 (Hit@3 값을 옮겨 적은 실수). 테스트셋을 돌리기 전에 리포트와 대조해서 바로잡음
  - 동점이면 dense
- 영어 질문은 이 실험과 관계없이 dense를 유지함

한국어 튜닝용 셋 (32문항):

| 설정 | Hit@5 | MRR | 지연 p50 | 지연 p95 |
|---|---|---|---|---|
| dense | 0.84 | 0.766 | 7ms | 33ms |
| rerank, 기존 영어 전용 모델, 목록당 3개 (참고) | 0.91 | 0.674 | 316ms | 406ms |
| rerank, 다국어 모델, 목록당 3개 | 0.91 | **0.891** | 483ms | 745ms |
| rerank, 다국어 모델, 목록당 5개 | 0.94 | 0.885 | 818ms | 1219ms |
| rerank, 다국어 모델, 목록당 8개 | 0.97 | 0.911 | 1359ms (예산 초과) | 1946ms |

예산 안에 드는 설정 중 MRR이 가장 높은 목록당 3개를 고름.

한국어 테스트셋 (43문항, 목록당 3개로 1회만 실행):

| 설정 | Hit@3 | Hit@5 | Hit@10 | MRR | 지연 p50 |
|---|---|---|---|---|---|
| dense | 0.72 | **0.77** | **0.81** | 0.609 | 9ms |
| rerank | 0.72 | 0.72 | 0.74 | **0.690** | 418ms |

- **결과**: MRR은 올랐지만 보조 조건(Hit@5가 dense보다 낮지 않을 것)에서 탈락함 (0.77 → 0.72). 규칙대로 한국어 기본값은 dense를 유지함
  - 목록당 5개로 테스트셋을 다시 돌리지는 않음. 결과를 보고 설정을 고르는 셈이 되기 때문
- **오른 문항**: 7문항의 정답이 1위로 올라옴 (k009, k017, k027, k033, k035, k040, k041). MRR 상승은 여기서 나옴
- **Hit@5에서 빠진 두 문항은 원인이 다름**
  - k024: dense에서 5위였는데, 목록당 3개만 후보로 쓰니 후보에 들지 못함. 후보 수를 줄인 대가
  - k004: dense에서 2위였던 정답을 재정렬 모델이 후보 6개 중 꼴찌로 내림. 모델의 판단 실수
- **Hit@10도 0.81 → 0.74로 떨어짐**: 후보가 최대 6개라, dense에서 6~10위에 있던 정답(k015, k030)도 결과에서 사라짐. LLM에는 상위 5개만 전달되므로 답변에는 영향이 없음
- **튜닝용 셋이 못 잡은 것**: 튜닝용 셋에서는 Hit@5도 올랐음(0.84 → 0.91). 후보를 줄였을 때 정답이 후보에서 빠지는 위험이 드러나지 않았음
  - 튜닝용 셋은 문서를 보면서 쓴 질문이라 dense에서도 정답이 상위권에 몰려 있음 (Hit@3: 튜닝용 0.81, 테스트셋 0.72). 이 차이 때문일 수 있음
- **영어 전용 모델로 한국어를 재정렬하면 오히려 나빠짐**: 튜닝용 셋 MRR 0.674로, 재정렬을 안 한 dense(0.766)보다 낮음
  - 그래서 `rerank` 모드를 켰을 때 한국어 질문은 다국어 모델을 쓰도록 언어별 설정을 둠 (`RERANKER_MODEL_NAME_KO`, 언어별 후보 수 `RERANK_POOLS`)
  - 기본값(dense)에는 영향이 없음
- **코드 변경 뒤 확인**: 설정 기본값만으로 다시 돌려 영어 튜닝용 셋 0.969(v6과 같음), 한국어 튜닝용 셋 0.891을 재현함

**답변 품질 (참고용, 결정에는 쓰지 않음)**

## 기타 관찰

- **LLM 판정의 오탐**: v3 dense에서 q017은 검색 실패 후 "컨텍스트에 정보가 없다"고 올바르게 답했지만, 판정 모델은 이를 환각으로 표시함.
- **키워드 커버리지는 거친 지표**: q030은 판정 정확도가 5점인데 답변에 `APIRouter`라는 이름이 없어서 커버리지는 0. 두 지표를 함께 봐야 함.
- **판정 점수 범위 강제**: 범위를 설명에만 적어 뒀을 때 판정 모델이 10점 척도로 넘어가 평균이 9점대로 나온 적이 있음. 이후 JSON 스키마의 `minimum`/`maximum`으로 1~5를 강제하고, 벗어나면 평가를 실패시킴.
